If you work with databases and use an ORM, you have probably hit the same wall I did. ORMs are great at mapping tables to objects. They start to hurt when the query gets serious: aggregations, careful joins, report shapes that do not match one model per table. You fight the ORM, drop to raw SQL, then write mapping glue by hand.

Not every `SELECT` returns something that fits one ORM model. SQL is the better language for data access. The best ORMs I have used, like [Drizzle](https://orm.drizzle.team/), win because they stay close to SQL. I wanted to go further: SQL in version control, typed Python generated from it, and no boilerplate in between.

That is why I built **[nORM](https://github.com/devfros/nORM)** (no ORM) and shipped **v0.1.0** this week.

- **Docs:** [devfros.github.io/nORM](https://devfros.github.io/nORM/)
- **Repo:** [github.com/devfros/nORM](https://github.com/devfros/nORM)
- **Playground**: [norm-play.vercel.app](https://norm-play.vercel.app/)
- **Release:** [v0.1.0](https://github.com/devfros/nORM/releases/tag/v0.1.0)

nORM is an alternative to using an ORM for everything. Right now the generator is Python only. I plan migrations and more language backends later; after that it could replace an ORM entirely if you want that. Today it is sqlc-style workflow plus dynamic query stuff you would otherwise write in Python.

The workflow is inspired by [sqlc](https://github.com/sqlc-dev/sqlc). If you already use sqlc and it is enough, keep it.

## SQL in, Python out

You write schema and queries in SQL. `norm generate` produces models and repo classes. Open a generated method and the SQL is right there. No hidden query layer.

**Schema** (`norm_in/schema.sql`):

```sql
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    name text NOT NULL,
    blocked bool DEFAULT false
);
```

**Queries** (`norm_in/repositories/users_repo.sql`):

```sql
-- repo_name: UsersRepo

-- name: get_user :one
SELECT * FROM users WHERE id = :id;

-- name: list_users :many
SELECT * FROM users ORDER BY name;
```

**Generated** (trimmed from the [Python tutorial](https://devfros.github.io/nORM/tutorials/python)):

```python
class UsersRepo:
    async def get_user(self, id: int) -> User | None:
        query = """
            SELECT
              users.id AS id,
              users.name AS name,
              users.blocked AS blocked
            FROM users
            WHERE users.id = %(id)s
        """
        params = {"id": id}
        async with self.db.cursor() as cur:
            await cur.execute(query, params)
            result = await cur.fetchone()
            ...
        return User(id=result[0], name=result[1], blocked=result[2])
```

**Your app:**

```python
from norm_out.users_repo import UsersRepo

async with get_db() as db:
    repo = UsersRepo(db)
    user = await repo.get_user(id=42)
```

That is the baseline: the same sqlc-shaped loop (SQL files, generate, call typed methods), without hand-written row mapping.

## Three steps

1. Write SQL (schema + repository queries).
2. Run `norm generate`.
3. Import the generated package and call repo methods from your app.

`norm init` scaffolds `norm.yaml` and folders. `norm check` is useful in CI: if a query references a missing column or a parameter type does not match, generation fails before runtime.

## Where nORM goes past plain codegen

sqlc stops where the app still needs runtime composition: optional filters on list endpoints, user-chosen sort columns, partial updates, nullable joins. nORM adds macros so that logic stays in SQL and the generator expands it.

**Dynamic filtering.** Prefix a parameter with `_` to make a predicate optional. One query can cover many filter combinations instead of string-building in Python.

```sql
-- name: search_authors :many
SELECT * FROM authors
WHERE name = :_name AND rating > :_min_rating;
```

The [dynamic filtering guide](https://devfros.github.io/nORM/guides/dynamic_filtering/) walks through the generated API and how nORM prunes the `WHERE` tree at runtime.

**Dynamic sorting.** Use `n.ord()` in `ORDER BY` when the client picks the column and direction.

```sql
-- name: list_authors_sorted :many
SELECT * FROM authors a
ORDER BY n.ord(a, :order_by, :desc), a.id ASC;
```

Generated methods take a `Literal[...]` for allowed columns and validate before running the query. Details: [dynamic sorting guide](https://devfros.github.io/nORM/guides/dynamic_sorting/).

More macros (partial updates, join embedding, and others) are in the [overview](https://devfros.github.io/nORM/overview/what-is-norm/) and the [guides](https://devfros.github.io/nORM/guides/select).

## How it works

Parsing and dialect work run through [sqlglot](https://github.com/tobymao/sqlglot). nORM reads DDL, repository SQL, and macros, then reasons about types and SQL shape before codegen. Postgres, SQLite, MySQL, ClickHouse, and DuckDB share that path. The CLI, generators, macros, and `norm.yaml` config are nORM itself.

The project has broad test coverage. v0.1.0 is the first public release, but the core generate path is what I have been hardening for months.

## What is in 0.1.0

**Included:** Python generator (async or sync, Pydantic or dataclasses via `norm.yaml`). CLI: `norm init`, `norm generate`, `norm check`, `norm schema pull` for Postgres introspection.

**Not yet:** Rust, Go, and TypeScript generators. No migrations command in 0.1.0; I plan to add migrations later. Until then, keep using your usual tool for schema changes.

## Try it

```sh
pipx install norm-cli
norm init
norm generate
```

Python 3.12+ for the CLI. Work through the [Python tutorial](https://devfros.github.io/nORM/tutorials/python), then try dynamic filters or sorting on a small schema.

If something feels off, [open an issue](https://github.com/devfros/nORM/issues) or send a PR.
